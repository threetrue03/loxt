## 먼저 확인할 중요한 문제 5개

1. **긴 스크립트의 카드 미리보기가 8줄에서 끝난다.** 목록을 이미 요약한 뒤 다시 요약하면서 실제 전체 줄 수를 8로 덮는다. 패키지 화면에서 24줄 문서가 목록 `8/8`, 상세 `24`로 확인됐고 더 보기 버튼이 없었다. 원문 삭제가 아니라 목록 메타데이터 오류다. Work·Live·웹의 공통 반환 경로를 함께 고쳐야 한다. **V04**
2. **메모에 보이는 문구도 서식 경계를 넘으면 검색하지 못한다.** `스타일` + 굵은 `검색`은 화면에 `스타일검색`으로 보이지만 검색 결과가 0개였다. 일반 문구는 1/1로 검색됐다. 목차 추가와 함께 메모 탐색 신뢰성을 개선해야 한다. **V07**
3. **많은 기록의 보관함 초기화가 느리다.** 예시 메모 3,000개 재개방 중앙값은 6.11초, 전체 목록 JSON은 11.24MB였다. 실제 앱의 화면 전환 시간이나 기존 iPad 3초 지연을 직접 측정한 수치는 아니지만, 초기 파일 확인·전체 목록 전송 비용을 줄일 근거는 있다. **V14·V15**
4. **삭제한 폴더를 일반 휴지통 복구로 원래 구조에 돌려놓지 못한다.** 기록 내용은 살아 있지만 폴더 계층은 사라지고 루트에 모인다. 같은 세션의 Ctrl+Z는 계층까지 복원한다. 두 동작의 차이를 먼저 안내하고 복구 정책을 정해야 한다. **V09**
5. **선택·드래그의 표현과 취소 동작이 부정확하다.** 폴더·메모·PDF·그리기·녹음을 함께 선택해도 `6개 녹음`으로 표시됐다. 드래그를 Esc로 취소하면 그다음 첫 클릭이 무시되고 두 번째 클릭은 정상 작동했다. **V02·V06**

현재 데이터 본문 손실이나 핵심 녹음 기능 전체 불능을 확인한 **P0는 없다**. 목록 오류를 원문 손실로, 합성 측정을 모든 사용자 환경의 성능으로 표현하지 않는다.

### 테스트 환경·스크립트의 실패와 앱 문제 구분

- 대상 테스트의 최초 메모 5개 실패는 sandbox TEMP의 이름 변경 권한 문제였다. TEMP/TMP를 작업 공간의 예시 위치로 설정한 재실행에서 5/5, 대상 전체 22/22 통과했다.
- UI 예시 PDF를 만드는 최초 호출은 조사 스크립트가 `PDFs.import(bytes, name, folder)`에 경로 문자열을 잘못 넘긴 오류였다. 올바른 바이트 인수로 수정했으며 앱 결함으로 집계하지 않았다.
- 드래그 Esc 뒤 첫 클릭의 타임아웃은 실제 클릭 소실을 드러냈다. 이후 상태를 수치로 기록하고 두 번째 클릭 정상까지 확인했다.
- 더 보기 버튼 대기는 실제 목록 요약 오류 때문에 실패했다. 없는 버튼을 성공으로 가정하지 않고 목록/상세 개수와 버튼 0개를 기록했다.
- 모바일 메모 첫 탐색 타임아웃은 화면 밖 카드의 본문이 지연 렌더되는 정상 구조에 맞지 않는 조사 선택자였다. 카드 프레임을 먼저 스크롤하는 경로로 보완한 최종 검증은 완료했다.
- 실패 중간 로그·JSON도 보존했다. 최종 완료는 모든 UX가 정상이라는 뜻이 아니라 **문제를 포함한 조사 절차를 완료했다**는 뜻이다.

## 요청한 세 항목의 권장 설계

### V01 — 메모 우측 목차

**공통 MemoEditor 안에 넣는 방향**을 권장한다. 독립 메모, Work·Live 녹음 중 메모, 저장된 스크립트 옆 메모, 오른쪽 폴더 탭, 전체화면, 읽기 전용 메모가 같은 동작을 제공하도록 한다.

```text
[<] 저장됨   파일 이름·경로·날짜    [찾기][목차][…][내보내기 ▾][전체화면]
┌ 메모 본문 ──────────────────┬ 목차                     [×] ┐
│ # 회의 정리                 │ ▾ 회의 정리                  │
│ ## 결정 사항                │    ▾ 결정 사항               │
│ ### 후속 작업               │       ▾ 후속 작업            │
│ #### 일정                   │          일정                │
└────────────────────────────┴───────────────────────────────┘
```

- 넓은 화면: 메모 오른쪽 **내부** 패널. 260px 전후는 초안이며 실제 메모 최소 폭 테스트 후 확정한다. 전역 오른쪽 브라우저 패널과 혼동하지 않는다.
- 좁은 녹음 옆 메모·모바일: 해당 메모 위에 겹치는 패널. 제목을 선택하면 본문으로 이동하고 닫는 방향. 앱 자체를 가로로 늘리지 않는다.
- 기존 SUIT·다크/라이트 토큰·얇은 테두리와 패널 애니메이션을 유지한다. 빠른 열기·닫기, reduced motion, Esc·포커스 복귀를 처리한다.
- 문자열 정규식이 아니라 실제 `heading` 블록과 `props.level=1~4`를 읽는다. 코드 블록의 `#`는 목차가 아니다.
- h1→h3이면 가짜 h2를 생성하지 않고 가장 가까운 앞선 낮은 레벨의 제목 아래에 넣는다. 부모가 없으면 루트에 둔다.
- 같은 제목·빈 제목·한글·이모지·굵게·링크·긴 제목·중첩 children을 처리한다. 이동 대상은 문구가 아닌 **block ID**다.
- 제목 추가·이름 변경·삭제·이동·원격 갱신 후 tree와 현재 위치를 맞춘다. 입력 커서·IME·실행 취소 이력을 임의로 변경하지 않는다.
- 읽기 전용 메모에서도 목차 이동은 허용한다. 제목이 없으면 “제목을 추가하면 목차가 표시됩니다”를 보여준다.
- 시각적 계층이면 중첩 nav/list로 시작할 수 있다. 실제 ARIA tree를 사용하면 방향키·Home/End·Enter·roving tabindex까지 구현해야 한다.
- 기존 h1–h3 문서를 재작성하지 않는다. h4 스키마·서식 메뉴·slash 메뉴·`#### ` 입력·Esc 되돌리기·저장·재실행·Markdown/HTML/PDF 내보내기를 함께 검증한다.
- 목차 닫힘 상태에서 제목 위치 DOM 측정이나 스크롤 observer를 돌리지 않는다. 제목 구조·문구가 그대로인 일반 입력은 tree 전체를 불필요하게 갱신하지 않는다.

실제 10,000블록·500제목의 제안 추출 함수는 중앙값 0.70ms였다. 이는 **설계용 추출 함수**이며 목차 UI가 구현·최적화됐다는 증거는 아니다. 처음부터 별도 Worker·영구 목차 인덱스를 도입할 근거도 부족하다.

### V02 — 파일 종류·선택 설명

사용자가 적은 녹음·스크립트·그리기·PDF·폴더에 **이미 존재하는 메모**도 포함해야 한다.

| 현재 저장 상태 | 분류 기준 | UI 표시 방향 |
|---|---|---|
| 일반 녹음·변환 전 기록 | 오디오가 있는 일반 기록 | 녹음 |
| 녹음 + 변환된 스크립트 | 오디오 존재 + 변환 결과 | 녹음, 필요 시 “스크립트 포함” 보조 표현 |
| 원본을 분리한 스크립트 | `audioMissing` | 스크립트 |
| 휴지통에 분리된 원본 | `kind=audio` | 녹음 원본 |
| 독립 메모 | `kind=memo` | 메모 |
| 새 그리기 | `kind=pdf`, `documentType=drawing` | 그리기 |
| 가져온 PDF | `kind=pdf`, 그리기 아님 | PDF |
| 폴더 | `folder:<path>` 선택 키 | 폴더 |

- 단일: 제목 + 실제 종류. 같은 종류 다중: “PDF 3개”, “메모 2개”.
- 혼합: **“6개 항목”**을 우선하고 여유가 있으면 “폴더 1 · 녹음 2 · PDF 1 · 메모 2”를 보조 표시한다.
- 녹음+스크립트는 현재 하나의 기록 ID이므로 두 개로 집계하지 않는다. 폴더 하위 파일 수도 사용자가 직접 선택한 수와 섞지 않는다.
- 배지·카드 아이콘·그리기 미리보기·목록 상태·이름 변경·관리 메뉴 aria-label을 동일 분류로 맞춘다. 기존에 제거한 카드 상태 배지를 모두 다시 추가하는 제안은 아니다.
- 여러 항목 이동/휴지통 처리는 이번 격리 테스트에서 정상이다. “우클릭한 하나만 처리”하는 과거 버그가 현재 재발했다고 보고하지 않는다.

### V03 — 새 녹음 사이드바 테두리

Work·Live의 `.sidebar-create.primary`에 있는 **상시 border만** 제거하는 것이 요청에 맞다. 측정한 실제 테두리는 디스플레이 배율이 반영된 `0.8px solid rgb(60,60,57)`였다. 토글·홈·파일 불러오기와 정렬·패딩·아이콘 크기를 맞추고, keyboard focus-visible·hover·disabled·현재 작업으로 돌아가기 표시를 함께 없애지 않는다.

## 중요한 버그의 재현·기대 결과·해결 위험

### V04·V05 — 카드의 8줄 이후 표시

재현: 예시 스크립트 24줄 저장 → Live 오른쪽 폴더 탭 → 카드 미리보기 확인 → 실제 목록·상세 API 비교.

```json
{
  "listSegments": 8,
  "listCount": 8,
  "detailSegments": 24,
  "moreButtonCount": 0
}
```

기대: 목록은 첫 8줄만 포함하더라도 `segmentCount=24`를 유지하고 더 보기로 상세를 읽는다. 실제: Library.listSummary 이후 반환 wrapper에서 summary가 또 호출돼 8이 전체 수로 저장된다. 별도 웹 RPC도 12줄 문서의 전체 수를 8로 보내고 상세는 12줄을 유지했다.

권장: summary를 반복 호출해도 원래 총수가 바뀌지 않게 한다. 새 변환·수정 결과가 전체 본문인지 이미 요약된 결과인지 구분해야 하며, 오래된 count를 무조건 보존해 새 변환 결과와 어긋나는 회귀도 막아야 한다.

V05는 다른 원인이다. 더 보기 함수가 `closest('[data-workspace]')` 실패 시 Work를 사용한다. 오른쪽 패널은 이 래퍼 밖이어서 Live ID를 Work로 조회할 수 있다. 실제 함수/API 재현에서 Work 요청은 “문서를 찾지 못했습니다”, Live 요청은 12줄 정상이다. **현재 화면에서는 V04가 버튼을 가려 V05 클릭을 실행하지 못했다.** V04 수정 후 메인/패널 × Work/Live × 카드/작은 카드에서 직접 확인해야 한다.

### V06 — Esc 뒤 첫 클릭

재현: Ctrl+A → 카드 길게 누름 → 드래그 시작 → Esc → 마우스 놓기 → 메모 카드 클릭.

기대: 취소되고 다음 클릭은 정상. 실제: 첫 클릭은 파일을 열지 못했고 두 번째는 정상이다. `cancel()`은 gesture만 지우고 suppress 플래그를 유지한다. 기존 pointerup은 gesture가 없어 즉시 반환해 플래그 해제 경로를 건너뛴다.

취소 시 즉시 해제와 정상 드롭의 합성 클릭 억제를 구분해야 한다. 무조건 즉시 해제하면 드래그 완료 직후 카드가 저절로 열릴 수 있다. 영역 선택·카드 드래그·pointercancel·페이지 이동 취소와 정상 드롭을 함께 검증한다.

### V07·V08 — 메모 검색

예시 본문: `스타일` 일반 텍스트 + `검색` 굵은 텍스트. `스타일검색` 검색은 0개, 일반검색은 1/1이었다. TextNode별 indexOf로는 서식 경계를 가로지르는 문자열을 찾지 못한다.

블록 텍스트와 실제 DOM offset 대응을 만들되 다른 문단을 임의로 이어 잘못 일치시키지 않는다. 한글·링크·강조·수식·표·중첩 토글의 검색 범위를 정의한다. 많은 Range를 만드는 검색의 입력 비용은 실제 큰 DOM으로 추가 측정한다. 첫 결과 표시·Enter·Shift+Enter·현재 강조/스크롤을 함께 맞춘다.

### V09 — 폴더 복구

재현: 폴더 `묶음/하위`에 기록 저장 → 상위 폴더 휴지통 → 일반 복구. 기록의 folder는 빈 문자열, 원래 폴더 계층은 복구되지 않았다. 관리 undo는 계층까지 돌려놓았다.

1차 수정은 현재 정책을 삭제 확인에 정확히 안내하는 것이다. 완전한 폴더 복구는 원래 경로·빈 폴더·동명 충돌·일부만 복구·원본 분리 기록의 연결을 설계해야 한다. 내용/ID를 새 문서로 복사하는 우회 방식은 피한다.

### V11 — 모바일 도구

390px 터치 에뮬레이션에서 검색 34×32, 편집 도구 36×32, 내보내기 약 106×32, 전체화면 34×32px였다. CSS의 coarse-pointer 44px 규칙이 뒤의 기본 32px 규칙에 덮인다. 이는 **의도한 44px 목표와 다른 상태**이며 32px라는 이유만으로 모든 접근성 규격에 실패했다고 단정하지 않는다. 물리 iPad·손가락·펜 조작과 좁은 도구 줄을 추가 검증해야 한다.

## 성능 측정과 해석

### 보관함

각 문서는 예시 메모이며 미리보기 1,500문자를 포함했다. 재개방 3회 중앙값, snapshot/필터 연산은 반복 측정했다. 디스크 캐시·OneDrive·동시 작업·실제 문서 내용에 따라 달라진다.

| 기록 수 | 최초 initialize | 재개방 중앙값 | 목록 JSON | snapshot 복사 중앙값 | 필터·정렬 중앙값 |
|---:|---:|---:|---:|---:|---:|
| 100 | 239ms | 242ms | 0.375MB | 0.97ms | 0.021ms |
| 1,000 | 2,524ms | 2,221ms | 3.75MB | 7.90ms | 0.144ms |
| 3,000 | 8,294ms | 6,108ms | 11.24MB | 25.34ms | 0.586ms |

우선순위는 순차 파일 확인·반복 lookup과 전체 목록/미리보기 전달이다. 이 조건에서 필터·정렬만 캐싱한다고 큰 개선이라고 말할 근거는 없다. 초기화 개선은 손상 인덱스·누락 원본·중단 녹음·폴더 변경 journal의 복구를 생략해서는 안 된다.

### 메모

| 블록 수 | UTF-8 JSON | 전체 복제 블록 patch 비교 | 본문 검증 | 미리보기 생성 | 초안 직렬화 | 제안 목차 추출 |
|---:|---:|---:|---:|---:|---:|---:|
| 100 | 41.8KB | 0.248ms | 0.444ms | 0.312ms | 0.085ms | 0.007ms |
| 1,000 | 419KB | 2.217ms | 2.582ms | 1.190ms | 1.145ms | 0.051ms |
| 10,000 | 4.20MB | 27.085ms | 27.310ms | 13.854ms | 11.757ms | 0.699ms |

10,000블록에서 **변경 없는 블록 참조를 유지한** patch 비교는 2.533ms였다. 편집기가 매 입력마다 전체 블록을 복제한다고 가정하지 않았다. 실제 1,000블록의 부분 저장 10회는 중앙값 **12.69ms**, 최대 **20.93ms**였다. 이번에 기존 “모든 작업이 3초 지연”을 다시 재현한 것은 아니다.

미리보기 추출을 필요한 문자 수에서 일찍 끝내는 개선부터 고려한다. 검증·초안·journal을 없애는 대신 변경 블록 검증과 직렬화 빈도를 검토한다. 표·한글·링크·중첩 순서, 본문 제한과 복구를 유지해야 한다.

### 원격 PDF와 모델 캐시

- 원격 PDF 실제 모듈에 서로 다른 30개 scale 요청을 즉시 취소해도 preview RPC 30개가 발행됐다. UI 결과를 무시하는 cancel과 원격 작업 취소는 다르다. 이 실험은 서버 큐 24개 제한이나 실제 Safari·90MB 문서의 래스터를 통과시키지 않았다. 큐가 무한하거나 이번에 iPad가 멈췄다고 보고하지 않는다.
- 모델 검색 예시 캐시 40개를 24시간 지난 상태로 두고 새 검색을 하면 41개·1,982,220바이트가 남았다. 네트워크 없이 모의 메타데이터로 확인했다. TTL은 만료 응답 재사용 방지이며 저장 공간 제한은 아니다.
- 문서 캐시와 목록 가상화는 적용 비용이 있다. 활성·저장 실패·dirty 문서를 버리지 않고, 화면 밖 선택·키보드·드래그를 보장해야 한다.
- 정적 파일의 해시 cache와 HTML 재검증은 버전 일치를 함께 설계한다. 민감한 API의 기존 no-store 정책을 정적 asset 정책과 섞지 않는다.

## 유지해도 괜찮은 부분

- 실제 혼합 항목 이동·휴지통·관리 실행 취소/다시 실행은 선택한 전체 대상을 처리했다. 이 계층을 다시 작성할 근거는 없다.
- 카드에는 이미 IntersectionObserver를 사용한 **본문 지연 렌더링**이 있다. 완전히 무최적화라고 표현하지 않는다. 많은 행 shell·observer·선택 DOM 비용은 별개다.
- 메모/PDF는 lazy import다. 분리된 JS·worker 크기의 합계를 앱 초기 메인 번들 크기라고 보지 않는다.
- PDF 현재 페이지 중심 렌더링, 모바일 pixel 제한, thumbnail window, 큰 원격 문서의 PC raster, 6페이지/4이미지 캐시, worker 분리는 유지할 가치가 있다.
- WebSocket RPC, 부분 patch, durable journal/checkpoint, 문서별 저장 큐·초안 보존은 안전성을 제공한다. 일괄 제거해 반응 속도를 높이는 방법을 권장하지 않는다.
- 모델 검색 debounce·generation 보호·pagination·동일 요청 dedup·TTL은 이미 있다. 작은 홈 3개 역할 카드에 가상화나 대형 상태 라이브러리를 넣을 필요는 없다.
- 확인한 메모 다크·라이트 화면에서 본문/제목/도구는 기존 SUIT와 색상 체계를 유지했고 페이지 가로 넘침은 없었다. 모든 버튼 색상·포커스 대비를 수치로 측정했다는 뜻은 아니다.
