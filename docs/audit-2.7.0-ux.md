# LOXT 2.7.0 준비 조사 — UI·UX·디자인

조사일: 2026-10-09. 확인한 앱 버전: `package.json:3`의 2.6.0. 이 문서는 **개선 제안과 코드 조사 결과**이며, 앱·설정·사이트·설치 파일을 변경한 기록이 아니다. 이 분담 조사에서는 GUI를 실행하지 않았다. 실제 화면 재현 결과는 통합 보고서의 검증 항목을 우선한다.

## 핵심 판단

1. 사용자가 요청한 목차는 공통 `MemoEditor`에 넣어야 독립 메모와 Work·Live 녹음 옆 메모가 같은 동작을 제공한다. 현재 제목 블록은 h1–h3만 허용하여 `####` 지원을 먼저 추가해야 한다.
2. 파일 종류를 나타내는 문자열과 아이콘의 공통 기준이 없다. 선택 드래그뿐 아니라 카드·미리보기·이름 변경·우클릭 접근성 이름까지 함께 맞추는 것이 좋다. 메모도 실제 존재하는 문서 종류이므로 누락하면 안 된다.
3. 새 녹음 테두리의 원인은 `styles.css:32`의 사이드바 전용 border 선언이다. 이 선언만 제거하고 키보드 포커스 테두리는 유지하면 기존 디자인을 보존할 수 있다.
4. 메모 검색은 서식 경계와 검색 이동 순서에 문제가 있다. 검색 결과의 수와 실제 문서를 함께 검증해야 한다.
5. 작은 화면의 메모 도구, 빈 공간 우클릭 메뉴, YouTube 모델 선택에 공통 UI와 다른 구현이 남아 있다.

## 사용자 요청 1 — 메모 목차 상세 제안

### 구조와 배치

기존 SUIT·색상 토큰·얇은 테두리·도구 버튼 크기를 사용한다. `memo-tools`에 `목차` 버튼을 두고, 해당 메모 편집기 오른쪽에서 패널을 연다. 전역 사이드바나 오른쪽 브라우저 패널을 재활용하지 않아 메모가 둘 이상 있어도 다른 문서의 목차가 섞이지 않도록 한다.

```text
[<] 저장됨   제목·경로·날짜      [찾기][목차][도구][내보내기 ▾][전체화면]
┌ 메모 내용 ─────────────────┬ 목차                  [×] ┐
│ # 회의 정리                │ ▾ 회의 정리               │
│ ## 결정 사항               │    ▾ 결정 사항            │
│ ### 후속 업무              │       후속 업무           │
│ #### 일정                  │          일정             │
└───────────────────────────┴───────────────────────────┘
```

- 데스크톱 넓은 메모: 기본 폭 약 260px, 본문 최소 폭을 지켜 열기. 이 수치는 디자인 제안이며 실제 패널 너비 테스트로 확정한다.
- 좁은 녹음 옆 메모·모바일: 해당 메모 위에 패널을 겹쳐 열고 제목을 누르면 본문으로 이동한 뒤 패널을 닫는 방향. 앱 전체 너비를 강제로 늘리지 않는다.
- `transform`·`opacity` 애니메이션, `prefers-reduced-motion` 적용. 빠른 열기·닫기에도 포커스가 유실되지 않도록 한다.
- 버튼에 `aria-expanded`, 연결된 패널 ID, 접근성 이름을 제공한다. 닫기·Esc 후 목차 버튼으로 포커스를 돌린다.
- 기본 선택은 계층형 `<nav><ul>` + 제목 버튼이다. 시각적인 tree만 필요하면 과도한 ARIA tree 구현을 피할 수 있다. 진짜 `role=tree`를 쓰면 WAI-ARIA의 상하좌우·Home/End·Enter·roving tabindex를 모두 구현한다.

### 데이터와 예외 규칙

1. 문자열의 `#` 정규식이 아니라 `editor.document`의 실제 `heading` 블록에서 `props.level` 1–4를 읽는다. 코드 블록의 `#`, 일반 문장, 수식은 목차로 넣지 않는다.
2. 제목 이동 키는 **블록 ID**다. 같은 제목이 두 번 나와도 각각 다른 블록으로 이동하며, 글자를 고쳐도 접기 상태·현재 위치를 가능한 한 유지한다.
3. h1→h3처럼 레벨이 빠지면 가짜 h2를 만들지 않는다. 가장 가까운 이전 낮은 수준 제목의 자식으로 배치한다. 선행 부모가 없으면 루트에 둔다. 원문의 level은 그대로 보존한다.
4. 빈 제목은 `제목 없음`으로 표시해 클릭·편집 가능하게 한다. 한글·이모지·링크·굵게 혼합 제목은 inline text를 이어 읽는다. 긴 제목은 줄바꿈 또는 최대 두 줄 + 전체 tooltip으로 처리한다.
5. 중첩 `children`까지 문서 순서로 순회한다. 접힌 토글 안 제목을 클릭하면 필요한 부모 블록을 연 후 이동하거나, 열 수 없는 경우 안내한다. 목차에서 임의로 내용·구조를 수정하지 않는다.
6. 삭제·순서 변경·원격 수정 이후 현재 항목을 블록 ID로 재확인하고, 없는 항목을 클릭해 예외가 나지 않도록 한다.
7. 독립 Work/Live 메모, Work 녹음 중 메모, Live 녹음 중 메모, 저장된 스크립트 옆 메모, 휴지통 읽기 전용 메모와 전체화면에 같은 구현을 적용한다. 읽기 전용에서도 탐색은 허용하고 편집은 막는다.
8. 제목 없는 문서는 `제목을 추가하면 목차가 표시됩니다`라는 빈 상태를 제공한다. 제목이 없는 것을 로딩 실패로 표시하지 않는다.

### 최적화와 보존

- 초기에는 선형 블록 순회로 충분하다. 목차 닫힘 상태에서는 DOM 위치 측정과 observer를 설치하지 않는다.
- 제목 구조와 문구가 바뀌지 않은 일반 문단 입력 때는 tree를 다시 만들 필요가 없도록 제목 signature/변경 블록 단위 갱신을 고려한다.
- 현재 제목 관찰은 메모 스크롤 영역을 root로 한 IntersectionObserver 등으로 처리하고, 모든 제목의 `getBoundingClientRect`를 매 스크롤마다 읽지 않는다.
- 기존 h1–h3 문서의 내용·ID를 마이그레이션 없이 보존한다. h4 지원 추가는 slash 메뉴·서식 메뉴·`#### ` 입력 변환·Esc 되돌리기·Markdown/HTML/PDF 내보내기를 함께 검증한다.
- 실제 큰 메모의 입력·스크롤 측정 전에는 가상화, worker, 전체 목차 인덱스 영구 저장을 필수라고 단정하지 않는다.

## 사용자 요청 2·3과 함께 맞출 범위

문서 종류는 UI의 단일 분류기로 정리하는 방향을 권장한다. 현재 메모는 `kind=memo`, PDF와 그리기는 `kind=pdf`와 `documentType=drawing`, 녹음 원본 전용은 `kind=audio`, 원본을 휴지통으로 옮긴 스크립트는 `audioMissing` 등의 필드가 있다. 세부 저장 모델은 통합 보고서의 실제 데이터 조사 결과를 따른다.

- 단일 항목 드래그: 제목 + 실제 종류를 표시.
- 같은 종류 다중 선택: `PDF 3개`, `메모 2개`처럼 표기.
- 혼합: `5개 항목`과 가능하면 `녹음 1 · 메모 1 · PDF 2 · 폴더 1` 보조 표현. 너무 길면 총 항목 수를 우선한다.
- 녹음+스크립트는 한 기록 엔터티이므로 파일 두 개로 이중 집계하지 않는다.
- 아이콘, 이름 바꾸기 input의 aria-label, 우클릭 메뉴 이름, 미리보기 이름까지 해당 분류를 공유한다. 사용자 요청이 카드 상태 배지를 다시 추가하는 것은 아니다.
- 새 녹음 사이드바만 상시 border를 없앤다. focus-visible, 활성 녹음으로 돌아가기, 모델 진행 상태의 경계까지 일괄 없애지 않는다.

## 안전하게 실행한 검증

앱 또는 사용자 데이터를 읽는 실행 API는 호출하지 않았다. `node --input-type=module`에서 **설치된** `@blocknote/core`의 `createHeadingBlockSpec({levels:[1,2,3],allowToggleHeadings:false})`를 실행해 `config.propSchema.level.values`를 확인했다.

```json
{"headingLevels":[1,2,3],"h4Allowed":false,"memoSplitNodeSearch":false,"visibleTextIncludes":true,"sidebarBoundarySource":true}
```

검색 반례는 `['프로젝트 ', '회의', ' 기록']` 세 노드와 `프로젝트 회의` 검색어로 현재의 개별 `indexOf` 알고리즘을 비교했다. 합쳐진 표시 문구에는 검색어가 있지만 개별 노드에는 없어 결과가 false다. **실제 메모 DOM을 생성한 재현이나 앱 스크린샷은 아니며**, 알고리즘 반례로만 기록한다.

초기 검증 명령에서 반환된 spec을 함수처럼 재호출해 TypeError가 발생했으나 이는 조사 스크립트의 실수였다. 호출을 바로잡은 검증은 정상 완료했다. 앱 결함으로 분류하지 않는다.

## 유지해도 괜찮은 부분

- 공통 Menu는 팝업 크기·뷰포트 제한·ResizeObserver·방향키·Escape·Tab을 이미 처리한다. 새 우클릭 메뉴를 이 로직과 맞추는 것이 새 메뉴 시스템보다 안전하다.
- FolderTree의 초기 expanded 상태는 빈 배열이다. 무조건 전체 하위를 여는 구현으로 단정할 근거는 없다.
- MemoHost는 lazy import로 메모 라이브러리를 분리하고, NoteCard는 IntersectionObserver와 제한된 프리뷰 로딩을 사용한다. 전체 화면을 가상화해야 한다고 추정하지 않는다.
- MemoEditor는 BlockNote sideMenu를 false로 설정해 사용자 요청대로 블록 관리 버튼을 숨기며, 저장 실패·초안 백업·최신 문서 확인을 제공한다.
- 기본 UI는 SUIT와 테마 토큰, 버튼 focus-visible, inert 메모 패널, reduced-motion을 이미 사용한다.

## 확인하지 못한 범위

이 분담에서는 Windows 실제 화면, Safari/iPad 실터치, 스크린리더, 모델 설치·추론, 대규모 메모 p95, 실제 테마 대비 수치를 측정하지 않았다. 이 항목의 결과를 구현 성공으로 주장하지 않는다. 통합 담당자의 별도 격리 프로필 화면 검증과 병합해야 한다.

## 공식 근거

- [BlockNote 제목 설정](https://www.blocknotejs.org/docs/features/blocks/typography): 제목 level을 구성할 수 있으므로 LOXT의 h4 제한은 라이브러리 자체의 제한이 아니다.
- [BlockNote 문서 구조](https://www.blocknotejs.org/docs/foundations/document-structure): block ID·type·props·children 기반 목차 설계.
- [WAI-ARIA Tree View](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/): tree 역할을 선택할 때 필요한 포커스와 키보드 규약.
- [Vercel Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md): 코드 검토 체크 기준. 프로젝트에서 사용자가 합의한 스타일·범위를 우선하며, 이 가이드를 그대로 새로운 디자인 요구로 취급하지 않는다.
