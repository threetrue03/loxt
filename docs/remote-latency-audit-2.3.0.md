# LOXT 외부 기기 → PC 반영 지연 재조사

2026-10-09. 사용자는 ‘모든 작업이 약 3초 뒤 PC에 반영된다’고 보고했다. 이번 작업은 조사와 보고만 진행했다. 앱·설정·버전·설치 프로그램·소개 사이트를 수정하지 않았으며, 실제 사용자 녹음·메모·PDF·모델을 변경하지 않았다. 조사 스크립트와 예시 데이터는 `test-results/remote-latency-audit-2.3.0/` 아래에만 생성했다.

## 결론

**외부 반영을 더 빠르게 만들 수 있다. 3초가 반드시 필요한 구조는 아니다.** 다만 사용자가 겪는 공통 3초의 단일 원인은 이번 조사만으로 확정하지 못했다.

PC에서 직접 편집할 때 즉시 보이는 것은 먼저 로컬 편집 상태를 그리기 때문이다. 같은 웹 화면에서도 자신의 메모 입력은 2–5ms 수준으로 표시됐다. 다른 기기 화면은 저장 확정 → 변경 알림 → 본문 조회 → 화면 갱신을 거친다. 두 종류의 시간을 동일한 ‘저장 속도’로 비교하면 안 된다.

정상 예시 환경에서 웹 메모 → PC는 약 0.30초, 폴더 생성 → PC는 약 0.02초였다. 고정 3초 동기화 타이머는 확인되지 않았다. 실제 환경의 3초를 설명하려면 전송 요청 시작 전 대기, 네트워크/브라우저 연결 대기, PC 처리와 화면 표시 시간을 구분해야 한다.

**현재 실행 중인 설치 앱의 제품 버전은 2.2.0.0으로 확인했다.** 프로젝트와 새 설치 파일은 2.3.0이지만 아직 실행 앱에 적용되지 않은 상태다. 두 버전의 작은 메모·폴더 정상 경로는 비슷했으므로 ‘2.3.0 설치만 하면 모든 3초 지연이 사라진다’고 결론 내릴 수 없다. 다만 2.3.0의 큰 PDF PC 렌더 경로는 2.2.0 모바일의 PDF 해석 부담을 줄이기 위해 추가한 별도 개선이다.

## 중요한 발견

1. 저장이 확정된 내용만 다른 화면에 반영한다. 메모와 완료된 필기는 일반적으로 250ms 묶음 저장을 사용한다. 이 대기와 작은 본문 처리만으로 모든 작업의 3초를 설명할 수는 없다.
2. 길게 그리는 한 획은 펜을 떼기 전까지 외부로 보내지 않는다. 예시의 2.216초 획을 그리는 동안 PC 획 수는 변하지 않았고, 뗀 뒤 51ms에 새 획이 표시됐다. 실시간 획 미리보기를 원한다면 내구 저장과 분리된 전송이 필요하다.
3. PDF는 작은 변경 패치를 올려도 저장 응답과 다른 화면의 본문 조회는 전체 필기를 반환한다. 예시 1만 획에서는 요청 376바이트에 응답 약 3.98MB였다. 저장 중 다음 저장은 앞선 응답을 기다리므로 큰 응답 전송이 후속 입력에도 영향을 줄 수 있다.
4. HTTPS 서버는 HTTP/1 계열이며 탭마다 SSE 연결을 만든다. 같은 브라우저에서 총 6개 SSE 연결을 점유시키자 일반 보관함 요청이 1초 동안 완료되지 않았고, 연결을 닫은 뒤 완료됐다. 여러 물리 기기가 하나의 브라우저 연결 한도를 공유한다는 뜻은 아니다.
5. 실제 Wi-Fi·iPad에서 발생하는 공통 3초를 직접 측정한 자료가 없다. 이 구간의 시간 추적이 부족하므로 Wi-Fi, OneDrive, GPU, SSE 중 하나를 원인으로 단정해서는 안 된다.

## 측정 조건과 결과

Windows, 실제 패키징 Electron 앱 + 승인된 Edge 웹, 별도 예시 프로필, **같은 PC의 127.0.0.1 HTTPS**. 실제 공유기/Wi-Fi RTT, iPad Safari, 사용자 문서, GPU 추론은 포함하지 않는다. 계측은 테스트 프로세스의 메모리 안에서만 적용했으며 제품 코드를 바꾸지 않았다. 각 기본 동작 5회 중앙값이다.

| 동작 | 설치 앱 2.2.0 | 패키지 2.3.0 | 해석 |
| --- | --- | --- | --- |
| 웹 메모 입력 → PC 본문 | 296ms | 306ms | 자신의 편집 화면은 별도로 1–5ms에 표시 |
| PC 메모 입력 → 웹 본문 | 302ms | 298ms | 양방향 모두 같은 저장 확정 흐름 |
| 자동 저장 대기를 생략한 직접 메모 RPC → PC | 41ms | 43ms | 현재 본문 조회 + 저장 호출을 포함한 값 |
| 웹 폴더 생성 → PC 표시 | 21ms | 21ms | 입력 자동 저장 대기 없음 |
| 웹 필기 종료 → PC 표시 | 이번 비교에서 미측정 | 296ms | 첫 획/장시간 유휴 후에는 대기가 짧아질 수 있음 |

2.3.0의 한 메모 입력 예시를 분해하면 요청 시작까지 263ms, PC 저장 처리 19ms, 변경 알림 생성은 입력 후 285ms, PC 알림 수신은 287ms, PC 본문 조회 13ms였다. 한 변경에 `memos:get`은 1회였고 불필요한 전체 목록 조회는 관측되지 않았다. 이전 2.1.1의 여러 캐시 본문/목록 재조회 문제가 그대로 남아 있다고 취급하지 않는다.

2.2.0 비교는 메모 양방향·직접 RPC·폴더 단계까지 완료됐다. 이후 모바일 문서의 이전 버전 탐색 UI와 조사 스크립트의 선택자가 맞지 않아 중단됐다. 이를 앱의 실제 PDF 기능 실패로 기록하지 않는다. 2.3.0의 모든 계측 단계는 완료됐으며 JS 오류는 없었다.

### 제어된 추가 실험

| 조건 | 관측 | 의미 |
| --- | --- | --- |
| 한 획을 2.216초 동안 그리기 | PC 획 수 5→그리는 동안 5→펜을 뗀 뒤 6, 종료 후 51ms | 획 미리보기는 작성 기기 내부에만 존재 |
| 원래 SSE 1개 + 추가 SSE 5개 | 1,009ms까지 일반 조회 미완료. 해제 후 전체 1,025ms에 완료 | 같은 브라우저 연결 점유에 따른 요청 대기 실제 재현 |
| 폴더 생성 전송에 인위적으로 2,500ms 삽입 | PC 표시 2,543ms | 입력/전송 대기만으로도 공통 수 초 지연이 만들어질 수 있음. 실제 사용자 네트워크 수치 아님 |

폴더/제목 변경은 메모 자동 저장 타이머와 별개다. 모든 종류가 비슷하게 3초라면 자동 저장 숫자만 낮추기보다 공통 전송/실행 대기부터 확인하는 편이 맞다.

### 본문 크기에 따른 서비스 비용

현재 2.3.0 서비스 직접 호출, 프로젝트 아래 별도 합성 보관함, 각 5회 중앙값. 네트워크와 React/SVG 표시 비용은 제외했다. PDF 객체마다 30개 좌표를 생성했고 한 객체만 수정했다.

| PDF 획 수 | 요청 패치 | 전체 응답 | 실제 필기 JSON 파일 | 저장 | 조회 | 관측된 이벤트 루프 최대 지연 |
| --- | --- | --- | --- | --- | --- | --- |
| 100 | 376B | 37,894B | 164,414B | 17.22ms | 3.27ms | 17.65ms |
| 2,000 | 376B | 793,594B | 3,323,614B | 93.94ms | 27.83ms | 39.78ms |
| 10,000 | 376B | 3,975,894B | 16,625,914B | 414.69ms | 134.18ms | 206.44ms |

100블록 합성 메모는 본문 약 180KB, 저장 15.93ms/조회 4.68ms였다. 1,000블록·약 1.82MB에서는 저장 62.45ms/조회 22.31ms였다. 메모 입력은 변경 블록이 아닌 전체 본문을 보낸다.

4MB 응답은 예를 들어 유효 전송 속도 20Mbps에서 순수 전송량 계산만 약 1.6초다. 이는 가정에 따른 계산이며 사용자의 Wi-Fi 속도를 측정한 결과가 아니다. 원본 PDF가 90MB라는 사실과 필기 JSON이 4MB라는 사실도 별개다. 2.3.0의 큰 PDF 페이지 이미지 개선만으로 필기 본문의 전체 전송/전체 저장 비용이 사라지는 것은 아니다.

## 해결 순서와 현실적 목표

1. **실제 3초의 공통 구간부터 계측.** 웹 탭 하나, 다른 문서 작업 없는 상태에서 폴더 생성과 짧은 메모 입력을 비교하고 Network의 Queueing/Stalled/TTFB, 송신 기기 긴 JS 작업, PC 처리 시간을 함께 기록한다. 오래된 실행본과 새 패키지를 구분한다.
2. **낭비가 확인된 전체 응답부터 줄이기.** 필기 저장 ACK 축소 → 문서 변경분 전파 → 수신 화면 부분 적용을 묶는다. 저장/백업/충돌 검사는 유지한다. Node `sync()`를 무조건 제거해 ‘빠른 저장’으로 만드는 방향은 피한다.
3. **실시간 느낌을 별도로 설계.** 완료 획의 빠른 전송과 작성 중 획의 임시 미리보기를 내구 저장과 분리한다. 메모 초안/완료 상태도 사용자에게 구분한다.
4. **다중 탭 전송 정리와 변경 재조회 보호.** SSE 공유 또는 다른 전송안을 선택하고, 놓친 목표 revision이 남도록 한다.

제안 목표는 정상 Wi-Fi에서 작은 클릭 작업 100–200ms 이내, 완료 획/짧은 메모 반영 150–300ms 수준이다. 아직 실제 Wi-Fi에서 달성한 수치나 보장치는 아니다. 네트워크 왕복·저장 내구성·기기 렌더링 비용을 0으로 만들 수는 없지만, 모든 작업이 3초 기다려야 할 이유도 없다.

## 그대로 유지할 부분

- 문서별 저장 직렬화, 원자적 파일 교환, 백업, revision 충돌 보호.
- 본문 확정 알림과 선택적인 목록 인덱스 기록의 분리.
- 공유 목록 조회와 오래된 응답 차단. 이번 작은 변경에서 중복 목록 재조회는 관측되지 않았다.
- 서버 알림은 변경 직후 발생한다. **15초 SSE heartbeat는 연결 유지용이고 동기화 주기가 아니다.** 서버의 10초 네트워크 확인도 일반 문서 동기화 주기가 아니다.
- PC 화면은 `backgroundThrottling: false`를 이미 사용한다. PC의 기본 백그라운드 타이머 제한을 현재 원인으로 가정하지 않는다. 외부 브라우저의 비활성 정책은 별개다.

## 확인하지 못한 범위

실제 iPad Safari·사용자 Wi-Fi에서의 3초, 사용자 문서 크기/획 수/메모 블록 수, 열린 탭 수, 실제 요청 재시도·대기, GPU/Live 동시 사용 중 서버 부하, 실기기 절전/브라우저 백그라운드 상태는 미측정이다. 기존 사용자 앱은 종료·업데이트하지 않았다. 따라서 가장 중요한 미확정 사항은 **사용자의 3초 중 어느 구간이 길어지는가**다.

원시 자료: `test-results/remote-latency-audit-2.3.0/results-2.3.0.json`, `results-2.2.0.json`, `body-results.json`. 최초 계측은 모바일 문서에서 보관함으로 돌아가는 선택자 오류로 중단됐고, 2.3.0 최종 계측에서는 절차를 맞춘 뒤 전 단계가 완료됐다. 테스트 선택자 오류를 제품 버그로 포함하지 않았다.
