# LOXT v2.7.0 사전 조사 — 성능·데이터 흐름

조사일: 2026-10-09 · 조사 대상: `package.json` **2.6.0**. 앱 코드·버전·설정·사용자 보관함은 변경하지 않았다. 이 문서는 다음 버전을 위한 조사 자료이며 v2.7.0 구현 또는 출시 완료를 뜻하지 않는다.

## 가장 중요한 결과

1. **대규모 보관함의 초기화가 실제로 느리다.** 격리된 3,000개 메모 보관함의 재개방 중앙값은 **6.11초**였다. 각 문서의 파일을 순차 확인하고 매번 배열에서 ID를 찾는 구조가 확인됐다.
2. **목록이 전체 보관함과 미리보기를 함께 운반한다.** 합성 메모 3,000개의 목록 JSON은 **11.24MB**였다. 폴더 변경·초기 접속·재동기화가 보관함 전체 규모에 영향을 받는다. 이는 전송 크기 측정이며 실제 Wi-Fi 지연 측정은 아니다.
3. **큰 메모에서 전체 검증·미리보기·초안 직렬화 비용이 남아 있다.** 10,000블록·4.20MB 메모의 서버 검증 중앙값 **27.31ms**, 미리보기 생성 **13.85ms**, 전체 초안 JSON 생성 **11.76ms**였다. 작은 메모의 실제 부분 저장은 정상적으로 빨랐다.
4. **원격 PDF 렌더 취소가 서버 요청을 취소하지 않는다.** 실제 `remotePDF` 코드를 모의 전송으로 실행하자 취소한 렌더 30개가 모두 preview RPC 30개를 발행했다. PC 작업 큐와 통신에 오래된 작업이 남을 수 있다. 실제 대형 PDF·iPad 멈춤을 이번 실험으로 재현한 것은 아니다.
5. **목차 자체의 데이터 추출은 우선 병목이 아니다.** 10,000블록·제목 500개에서 제안 추출 알고리즘 중앙값은 **0.70ms**였다. 처음부터 Worker를 추가하기보다 편집 상태와 분리한 재계산, 접힌 트리, 스크롤·포커스 보호를 우선하면 된다. 현재 메모는 h1–h3만 설정돼 **h4를 먼저 지원해야 한다.**

## 검증 조건과 원본 증거

- Windows `10.0.26200`, Node `v22.17.0`, AMD Ryzen 7 4800H, 논리 CPU 16개, RAM 16.50GB.
- 예시 데이터만 `test-results/audit-2.7.0/performance/` 아래에 생성했다. 사용자 녹음·메모·모델·설정 접근, 다운로드, GPU 추론, 원격 기기 접속은 하지 않았다.
- 첫 초기화는 규모별 1회, 이미 만들어진 같은 보관함의 재개방은 3회. OS 디스크 캐시는 초기화하지 않았다. CPU·디스크·OneDrive 상태의 영향이 있으며 실제 앱의 프로세스 실행부터 첫 화면까지 시간과 같지 않다.
- 함수별 비용은 15회 중앙값과 해당 15개 표본의 p95를 기록했다. 적은 표본의 p95는 장기 운영의 보장 수치가 아니다.
- 서버 저장은 실제 `Memos.save()`와 durable journal/fsync를 실행했다. 화면 그리기, 네트워크 왕복, 양쪽 기기의 이벤트 적용 시간은 포함하지 않았다.
- `measure.mjs`, `reopen.mjs`, `boundedness.mjs`, `measurements.json`, `boundedness.json`, 각 `.log`를 같은 디렉터리에 보관했다. 실행 실패 없이 완료했다.

## 중요한 항목의 정확한 위치와 검증 방법

### PF01 — 보관함 초기화

- `electron/library.cjs:79`: `initialize` 시작, `:113`: 문서 디렉터리 순회, `:160`: 반복 `findIndex`, `:161`: 전체 note JSON 비교. 인덱스가 정상이어도 전체 디렉터리 확인을 수행한다.
- 재현: `node test-results/audit-2.7.0/performance/measure.mjs`로 예시 100/1,000/3,000개 생성 후 `node test-results/audit-2.7.0/performance/reopen.mjs` 실행. 사용자 보관함으로 경로를 바꾸지 않는다.
- 기대: 기록 증가에 따라 시작이 늘더라도 인터페이스를 먼저 사용할 수 있고 복구 확인은 안전하게 진행. 실제: 초기화 promise가 모든 파일 확인 이후 완료.
- 개선 검증: 동일 예시를 다시 측정하고 손상 인덱스·누락 원본·중단 녹음·폴더 rename journal 회귀 검증. 동시성 증대는 디스크 부하와 RAM을 함께 측정.

### PF02·PF03 — 목록과 선택

- `shared/library-summary.cjs:2`: note의 다른 필드 전체 spread 뒤 segments 일부만 제한. 메모/pdfPreview가 그대로 남는다.
- `electron/web-services.cjs:24`: `library.list` 전체 summary 반환. `electron/main.cjs:272`: 앱도 전체 summary 사용.
- `src/LibraryView.jsx:86`: 필터·정렬, `:90`: 전체 visible items 구성, `:122`: 전체 notes.map. 실제 3,000개 필터/정렬 median 0.59ms이므로 이 연산만 먼저 캐싱해서 큰 개선이라고 주장할 근거는 없다.
- `src/NoteCard.jsx:11`: 행마다 IntersectionObserver. **본문이 화면 근처에서만 렌더되는 최적화는 이미 있다.** 완전히 무최적화된 전체 상세 카드 렌더링이라고 설명하면 틀린다.
- `src/useLibrarySelection.jsx:11`: selected×visible 비교, `:60`: 영역 선택의 모든 `[data-note-id]` DOM 조회 및 경계 읽기. 단순 Map보다 먼저 실제 많은 행의 포인터 프레임 비용을 측정해야 한다.
- 기대/검증: 1,000·5,000개 폴더·메모·PDF·녹음을 섞어 Ctrl+A, 범위 드래그, 화면 밖 스크롤, 다중 이동, 파일 종류 설명과 키보드 탐색을 검증. 가상화된 DOM만 대상으로 선택되면 새 버그가 된다.

### PF04·PF05 — 큰 메모

- `src/MemoEditor.jsx:68`: 검색 effect, `:71`: TreeWalker, `:74`: 일치별 Range 생성, `:78`: query와 state.blocks마다 반복.

## 사용자 요청: 메모 목차의 권장 구현 계약

목차는 오른쪽 상단 **목차** 버튼으로 오른쪽 내부 패널을 열고 닫는다. 기존 `.memo-toolbar`, SUIT, 테마 토큰과 다른 문서 패널의 애니메이션을 유지한다. 목차가 별도 보관함 항목이나 문서 본문 블록이 되면 안 된다.

1. `heading` 블록의 level 1~4와 `children`을 재귀 순회한다. 원시 Markdown 전체 정규식으로 추출하면 코드 블록 속 `#`, 링크, 이미지·중첩 블록, 변환 완료된 블록을 잘못 해석할 수 있다. 현재 공식 BlockNote API는 `editor.document`를 상위 블록 snapshot으로 설명하며 `forEachBlock`는 하위까지 순회한다. [BlockNote 공식 문서](https://www.blocknotejs.org/docs/reference/editor/manipulating-content)
2. 제목 level을 기준으로 가장 가까운 앞선 낮은 level에 연결한다. `# → ###`와 `####`만 등장하는 문서에서 없는 제목을 지어내지 않는다. 제목이 없으면 “제목을 추가하면 목차가 표시됩니다”. 빈 제목은 “제목 없음”, 중복 제목은 각각 다른 block ID로 구분한다.
3. 블록 ID를 이동 대상으로 사용한다. 항목 클릭 시 해당 메모의 스크롤만 이동하고 입력 커서·IME 조합·실행 취소 이력을 바꾸지 않는다. 기록의 메모 패널과 독립 메모 모두 검증한다.
4. 목차 패널을 열 때 제목 정보만 구독하고 저장중·타이머·환경 progress로 다시 추출하지 않는다. 파생 heading 데이터는 메모 단위로 유지한다. 10,000블록·500제목의 추출만 0.70ms였으므로 별도 Worker의 비용/복잡도를 지금 정당화할 근거는 부족하다.
5. React 외부 store snapshot은 기존처럼 변경 시 새로운 참조를 유지하되 선택한 heading 정보가 바뀔 때만 목차 갱신한다. 공식 문서의 변경 없는 snapshot 참조 보장과 subscribe cleanup 원칙을 따른다. [React 공식 문서](https://react.dev/reference/react/useSyncExternalStore)
6. 트리는 키보드·선택된 제목·접기 상태·긴 제목 말줄임과 전체 제목 접근을 제공한다. 모바일에서는 본문 최소 너비를 확보하거나 내부 오버레이로 표시한다. 빠른 열기/닫기 중 문서 focus/scroll이 초기화되면 안 된다.
7. `#`, `##`, `###`, `####` 입력·붙여넣기·MD 불러오기·저장·재실행·Markdown/HTML/PDF 내보내기, 제목 변경/삭제/중첩/이동과 목차 동기화를 확인한다. 현재 v2.6.0의 h4를 지원한다고 가정하지 않는다.

## 유지할 구조와 불필요한 변경

- 메모와 PDF는 lazy import다. PDF worker 2.42MB·MemoEditor 1.41MB의 크기만 보고 초기 메인 번들이 그 합계라고 보고하면 안 된다. `src/MemoHost.jsx:3`, `src/PdfHost.jsx:2`에서 분리돼 있다.
- PDF는 현재 페이지 중심, 모바일 약 5.24M pixel canvas 제한, thumbnail window 가상화, 원격 32MB 이상 PC raster 경로, 6페이지/4이미지 cache, 50ms/600point 미리보기가 있다. [PDF.js 공식 FAQ](https://github.com/mozilla/pdf.js/wiki/Frequently-Asked-Questions)의 canvas 메모리/범위 요청 관련 설명과 방향이 맞는다.
- PDF 검색 indexing worker와 렌더 worker는 분리돼 있다. 라이브러리 메인 작업 대기열과 문서별 durable 저장 대기열도 분리돼 있다.
- WebSocket RPC, 부분 문서 patch, fsync journal, 64회/1MB checkpoint, 본문 저장 완료 후 metadata 지연 기록은 유지할 가치가 있다. 실제 1,000블록 부분 저장은 10~21ms였으므로 안전성 장치를 제거해 “즉시 반영”을 만들 필요가 없다.
- 모델 검색 400ms debounce, generation 보호, 20개 pagination, 최대 200개 응답, 동일 네트워크 요청 dedup, 24시간 카탈로그/15분 검색 TTL은 이미 구현돼 있다. 작은 3개 홈 역할 선택 영역에 가상화는 필요하지 않다.
