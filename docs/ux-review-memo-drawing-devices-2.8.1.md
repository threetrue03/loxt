# LOXT 2.8.1 — 그리기·메모·기기 연결 UI/UX 조사 보고서

작성일: 2026-10-11 · 조사 대상: 현재 소스와 Windows 패키지 2.8.1

사용자가 요청한 변경 사항과 기기 연결 개선안을 함께 정리한 **조사 보고서**다. 이번 작업에서는 앱 코드, 설정, 설치 프로그램, 소개 사이트, 버전을 변경하지 않았다. 별도 예시 프로필에서 조사 스크립트와 화면 증거만 만들었다. 아래 설계는 아직 구현되지 않았다.

## 1. 핵심 결론

1. **그리기 전체화면은 이미 화면 전체 크기로 동작한다.** 메모와 다른 점은 내부 프레임의 여백·테두리와 종이의 맞춤 방식이다. 전체화면을 새로 만드는 대신 내부 프레임을 정리하고 종이의 너비/페이지 맞춤을 명확하게 해야 한다.
2. **Python 코드 블록도 이미 지원된다.** 시작 문법 입력과 완성된 Markdown 붙여넣기는 정상이다. 그러나 직접 타이핑한 닫는 백틱 세 개는 코드 내용으로 남는다. 사용자가 보여준 전체 입력 흐름을 마무리하도록 보완할 필요가 있다.
3. **목차 순서·글꼴·편집 메뉴는 요청대로 정리할 수 있다.** 현재 목차는 전체화면 왼쪽에 있고 H1–H4가 모두 12px이다. ‘…’ 안의 실행 취소/다시 실행/코드 복사는 메뉴를 없앨 때 접근 경로를 보존해야 한다.
4. **기기 중복은 모든 연결에서 발생하지 않는다.** 같은 승인 요청을 동시에 두 번 처리해도 한 건으로 유지된다. 기존 쿠키로 새로 페이지를 열어도 재승인은 생기지 않는다. 반면, 이미 승인된 브라우저에서 ‘연결 관리 → 새 연결 주소 → PC 재승인’을 수행하면 새 승인 기록이 추가되는 경로를 재현했다.
5. **기기 연결 화면은 기능보다 순서가 복잡하다.** 새 연결, 재접속, 인증서 초기 설정 주소가 한 화면에 섞여 있다. 홈에서 ‘내 기기 연결’로 이동하고, 연결 설정은 단계별 안내, 관리 목록은 승인 상태 중심으로 나누는 것이 좋다.

## 5. 메모·그리기 권장 설계

### 5.1 그리기 전체화면

현재 루트 전체화면은 메모와 그리기 모두 `x=0, y=0`이고 실제 창 콘텐츠 크기와 일치했다. 다크/라이트 결과도 같았다. 즉, **전체화면 기능이 없는 버그는 아니다.**

데스크톱 예시에서 그리기 작업 영역은 약 1233×705px, 너비 맞춤된 A4 종이는 약 1182×1672px이었다. 종이 높이가 더 커 스크롤이 필요한 것은 정상적인 비율 유지 결과다. 임의로 세로를 줄여 화면에 맞추면 필기 좌표와 내보내기 결과가 왜곡될 수 있다.

권장안:

- 전체화면에서 `.pdf-frame` 바깥 여백·테두리·라운드를 제거/축소하여 메모처럼 화면 끝까지 작업 영역을 사용한다.
- 문서 헤더, 필기 도구, 저장 상태, 내보내기, 전체화면 종료는 유지한다.
- ‘너비 맞춤’은 넓게 필기하는 모드, ‘페이지 맞춤’은 한 장을 모두 보는 모드로 유지한다.
- 전체화면 전환으로 임의 줌을 덮어쓰지 않는다. 맞춤 상태일 때만 새 작업 영역 크기로 재계산한다.
- 좁은 화면에서 페이지 패널을 열면 문서 일부를 덮는 현재 방식은 유지하되, 닫기와 선택 후 접기가 쉽게 보여야 한다. 데스크톱에서 열어 둔 페이지 패널을 창 축소 후 유지한 경우와 모바일 첫 진입을 구분한다.
- 무한 캔버스, 자동 페이지 크기 변경은 이번 요청에 포함하지 않는다.

```text
[‹] [페이지 ▾] [이름 편집] [경로 · 1/3]       [저장됨] [내보내기 ▾] [전체화면 종료]
[선택] [이동] [펜] [형광펜] [지우개] [T] [도형 ▾] [필기 옵션] [↶] [↷]
┌───────────────────────────────────────────────────────────────────────────┐
│                남은 화면 전체를 사용하는 문서/필기 영역                   │
└───────────────────────────────────────────────────────────────────────────┘
[검색]                           [1 / 3]                [줌] [맞춤 ▾]
```

### 5.2 코드 펜스와 ROS2

실제 2.8.1 검증:

| 조작 | 결과 |
|---|---|
| 빈 문단에 백틱 3개 + `python` + Enter | Python `codeBlock` 생성 |
| 이어서 `print("hello, world")` 입력 | 코드 내용 정상 |
| 다음 줄에서 백틱 3개 + Enter 직접 입력 | 백틱과 줄바꿈이 코드 내용에 남음 |
| 완성된 fenced Markdown을 일반 문단에 붙여넣기 | Python `codeBlock` 생성, 구분용 백틱은 남지 않음 |
| 코드 언어 검색에서 `ROS2` | ‘검색 결과가 없습니다’ |

닫는 펜스의 권장 동작은 **독립된 마지막 줄의 펜스 + Enter → 구분자를 제거하고 다음 일반 문단으로 이동**이다. 코드 문자열 안의 백틱, 중간 위치의 백틱, IME 조합, 기존 코드 블록 안에 붙여넣는 원문은 자동 변환하지 않아야 한다. Ctrl+Z로 입력 전 상태를 복원하고 원래 코드 내용과 언어를 보존해야 한다. 문서 전체를 Markdown으로 다시 파싱하는 방식은 블록 ID·첨부파일·목차·다른 기기 변경을 훼손할 수 있어 피한다.

ROS2는 하나의 프로그래밍 언어가 아니다. 공식 ROS 문서는 Python과 C++ 클라이언트 라이브러리를 구분한다. 따라서 ‘ROS2’ 하나를 Python 문법에 무조건 연결하는 방식보다 아래처럼 표시와 실제 문법을 함께 보여주는 것이 낫다. [ROS 공식 클라이언트 라이브러리 문서](https://repo.test.ros2.org/en/rolling/Concepts/Basic/About-Client-Libraries.html)

| 제안 항목 | 실제 처리 | 상태 |
|---|---|---|
| ROS2 · Python | 기존 Python 문법, `ros2-python` 입력/검색 별칭 | 권장 설계 |
| ROS2 · C++ | 기존 C++ 문법, `ros2-cpp` 별칭 | 권장 설계 |
| ROS2 · YAML / XML / Shell | 기존 각 문법을 사용하는 설정·launch·명령 분류 | 권장 설계 |
| ROS2 · msg / srv / action | ROS 인터페이스용 문법이 있는지 확인하고 테스트한 후 추가 | 추가 조사 필요 |
| ROS2만 입력한 경우 | 구체적인 언어 선택을 안내하거나 중립 텍스트로 보존 | 정책 확정 필요 |

단순 검색 별칭만 추가하면 저장 후 선택 이름이 ‘Python’으로 돌아갈 수 있다. ROS2 표시를 계속 유지하려면 표시용 분류와 실제 syntax language를 분리해 저장하고 구버전 문서도 읽히게 설계해야 한다. ROS 런타임 실행이나 패키지 설치 기능은 요청 범위가 아니다.

BlockNote의 Markdown 가져오기는 손실 가능성이 있는 변환이다. 기존 문서 저장은 블록 JSON을 유지하고, 붙여넣은 구간만 기존 파서로 처리하는 방향이 적절하다. [BlockNote 공식 Markdown 문서](https://www.blocknotejs.org/docs/features/import/markdown)

### 5.3 툴바·목차·‘…’ 제거

```text
[‹] [저장됨] [파일 이름] [경로 · 날짜 · 메모]
                                  [검색] [내보내기 ▾] [전체화면] [목차] [닫기*]
```

`닫기*`는 녹음에 연결된 메모 패널에서만 나타나는 기존 기능이다. 좁은 화면에서는 도구를 두 번째 행으로 보내고 순서를 유지한다. 메모 ‘…’ 제거는 그리기 페이지 관리 메뉴 제거를 의미하지 않는다.

메뉴 제거 후 기능 보존 제안:

- PC의 Ctrl+Z / Ctrl+Shift+Z는 유지한다.
- 터치 환경에서는 작은 실행 취소/다시 실행 버튼을 편집 도구 행에 제공한다. 두 버튼을 새 ‘…’ 메뉴로 다시 숨기지 않는다.
- 코드 복사는 코드 블록 언어 표시 옆의 작은 복사 버튼으로 옮긴다. 코드 블록 밖에 커서를 두고 복사했다가 오류가 나는 흐름을 줄인다.
- 복사 완료 표시는 기존 버튼 상태 애니메이션을 유지한다. 토스트를 추가하지 않는다.

목차 글꼴 제안값 — 제품 디자인 선택이며 성능/효과를 측정한 결과는 아니다:

| 단계 | 크기 | 굵기 | 비고 |
|---|---|---|---|
| # | 16px | 650 | 주요 장 |
| ## | 14px | 600 | 하위 절 |
| ### | 13px | 550 | 세부 항목 |
| #### | 12px | 400–500 | 가장 작은 제목 |

SUIT, 기존 다크/라이트 토큰, 들여쓰기, 접기/펼치기, 현재 위치 표시, 제목 클릭 이동을 유지한다. 크기는 트리 깊이가 아닌 **원본 heading level**에 따라 결정한다. H1 다음 H3처럼 단계가 건너뛰어도 올바르게 표시해야 한다. 긴 제목은 2줄까지 보여주고 터치 대상은 기존 44px 최소값을 유지한다.

## 6. 기기 연결 권장 설계

### 6.1 홈에서 진입

```text
홈 · Work                                            [내 기기 연결 →]
[새 녹음 시작] [파일 불러오기] [YouTube 불러오기]
내 보관함 …
```

Live 홈에도 같은 위치와 명칭을 사용한다. 연결 설정은 Work/Live별로 나누지 않는 앱 공통 설정이다. 버튼을 누르면 **서버를 자동으로 켜거나 인증서를 설치하지 않고** 해당 설정 탭으로 이동한다.

웹 기기의 홈에는 PC 서버 설정/다른 기기 승인 목록을 노출하지 않는다. 기존 ‘PC 연결됨 / 연결 관리’를 홈에서도 발견하기 쉽게 연결한다. 모바일에서 PC의 승인 권한을 얻는 기능은 추가하지 않는다.

### 6.2 최초 연결과 관리를 분리

```text
내 기기 연결
이 PC의 보관함을 같은 네트워크의 승인된 브라우저에서 사용합니다.
[연결 허용 켜짐]                     [서버 실행 중]

연결 요청 1개
[아이패드 · 이름/브라우저 정보]              [거절] [승인]

[새 기기 연결] [승인한 브라우저]

새 기기 연결
① 같은 네트워크 · PC 앱 실행 확인
② 인증서 설치/신뢰 안내 [안내 열기]
③ [QR]  연결 주소 [복사]       남은 시간 04:32
④ 이 PC에서 승인 → 연결 완료

대표 재접속 주소 [복사] [다른 네트워크 주소 ▾]
[문제 해결 ▾]
```

단계 표시의 ‘완료’는 확인된 상태에만 표시한다. 앱은 iOS 시스템 설정에서 인증서가 실제로 설치/신뢰됐는지 자동으로 보장할 수 없으므로, 서버 실행만으로 인증서 준비 완료를 표시하면 안 된다.

현재 서버는 Windows 기본 경로의 우선순위에 따라 주소를 정렬한다. 이 로직은 유지하고 대표 주소에 ‘권장’/네트워크 정보, 나머지에 ‘다른 주소’를 표시한다. 모바일에서 도달 가능하다는 사실은 같은 기기의 실제 접속으로 확인하기 전까지 보장하지 않는다.

### 6.3 기기 기록과 중복 처리

현재 목록의 실체는 **기기 하드웨어 식별자가 아니라 브라우저 승인 토큰**이다. 같은 iPad에서도 Safari, Chrome, 홈 화면 웹앱의 저장 공간이 달라질 수 있고, 같은 이름의 서로 다른 기기가 있을 수 있다. 이름/IP/User-Agent만으로 자동 병합하면 다른 사용자의 승인을 잘못 합칠 수 있다.

재현 결과:

1. 예시 서버에서 동일 요청 승인 호출 2회를 동시에 수행 → 목록 **1건**.
2. 이미 승인된 쿠키로 새 QR의 `/api/pair`를 다시 요청하고 PC에서 승인 → 목록 **2건**. API 경로 재현.
3. 실제 웹 연결 관리 UI에서 유효한 승인 상태로 새 주소를 제출하고 PC에서 다시 승인 → 목록에 **1건 추가**. 화면 흐름 재현.
4. 유효 쿠키가 있는 페이지를 새로 로드 → 추가 요청/승인 기록 없음.
5. 같은 문서 URL의 `#pair`만 바꾸면 연결 관리 창이 열림. 이는 `web.jsx`의 hashchange 동작이다.

최종 웹 조사에서는 기존 예시 승인 기록이 포함된 목록 수가 **6 → 정상 새로 열기 6 → 연결 관리에서 재승인 후 7**로 변했다. 이 절대 숫자는 반복 조사에서 만들어진 예시 기록이며 실제 사용자 기기 수가 아니다.

권장 정책:

- 정상 접속 중이라면 재승인을 우선 권하지 않고 현재 연결 상태를 보여준다.
- 유효한 인증 쿠키로 **같은 승인 세션임이 확인되는 경우**만 기존 기록 재사용/교체를 검토한다. 토큰을 교체한다면 열린 WebSocket과 CSRF 상태도 일관되게 갱신해야 한다.
- 만료/철회된 승인과 쿠키 삭제 후의 접속은 새 승인으로 처리한다. 편의를 이유로 PC 승인, QR nonce, 같은 출처/CSRF 검사를 생략하지 않는다.
- 사용자가 알아볼 수 있는 별명을 선택적으로 수정하게 하되 별명을 신뢰할 수 있는 기기 신원으로 사용하지 않는다.
- ‘승인 유효/만료’와 ‘현재 연결 중/최근 접속’을 분리한다. 온라인 표시는 실제 서버 소켓 상태를 사용하고 임의로 추정하지 않는다.
- 만료 목록은 별도로 접어서 보이고, 제거 전 대상과 영향을 확인한다. 사용자 문서/초안은 정리 대상이 아니다.

```text
승인한 브라우저
[민지의 iPad · Safari]    [접속 중]    [승인 유효 · 11월 10일까지]
최근 사용 방금 전                 [이름 수정] [승인 해제]

만료된 승인 2개 ▾
```

기기 이름 수동 입력을 연결의 필수 단계로 만들지 않는 것이 좋다. 자동 이름으로 연결하고, 필요하면 나중에 별명을 붙이는 방식이 가장 적은 입력을 요구한다.

### 6.4 재연결 동작별 안내

| 상태 | 먼저 보여줄 동작 | 추가 안내 |
|---|---|---|
| 정상 연결 | 현재 연결 정보 | 새 주소 입력은 부차적 도구로 둔다. |
| PC 서버/네트워크 중단 | 다시 연결 | PC 실행·같은 네트워크 확인. 재승인과 구분. |
| 승인 만료/해제 | 새 주소로 승인 요청 | PC에서 새 연결 주소를 복사하도록 단계 안내. |
| PC 주소/출처 변경 | 초안 사본 보관 후 새 주소 열기 | 기존 초안 보호와 복구 사본 가져오기 유지. |
| QR 만료/거절/다른 브라우저 사용 | 이유별 안내 + 새 QR 요청 | 하나의 ‘연결 실패’ 문구로 합치지 않는다. |

재승인 대기 취소는 모바일 대기 중단과 PC의 pending 요청 거절을 구분해야 한다. 서버의 대기 요청을 어떤 정책으로 정리할지는 구현 단계에서 별도로 검증한다.
