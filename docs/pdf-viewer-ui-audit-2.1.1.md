# LOXT 2.1.1 PDF 뷰어 UI·UX 조사 보고서

조사일: 2026-10-09 · 대상: 현재 소스와 패키징된 Windows 실행본 2.1.1, 같은 실행본이 제공하는 웹 화면.

이번 작업은 조사와 제안이다. 앱 코드·설정·사이트·버전을 수정하지 않았다. 모든 실행 검증은 별도 예시 보관함에서 진행했다. 참고 제품은 공식 문서와 공개 UI 이미지로 조사했으며, 유료 앱을 모두 설치해 사용해 본 것으로 표현하지 않는다.

## 1. 먼저 해결할 문제 5개

1. **PDF 두 손가락 확대가 문서 확대와 연결되지 않았다.** 사용자는 iPad·휴대폰에서 LOXT 전체가 확대되는 현상을 보고했다. 현재 `zoom` 상태는 하단 버튼과 맞춤 메뉴에서만 변경되고, 두 포인터의 확대·이동을 처리하는 코드가 없다. 읽기 상태는 브라우저 제스처에 맡기고, 필기 상태는 `touch-action:none`으로 막는다. PDF 내부 조작을 별도로 구현해야 한다.
2. **화면 폭에 맞춰 열리지 않으며, 맞춤 이후 화면 크기가 바뀌어도 다시 맞추지 않는다.** 모바일 390px에서 문서 폭은 595px로 시작한다. 768px에서 너비 맞춤을 한 뒤 320px로 줄이면 문서는 697px로 남았다.
3. **모바일에서 도구·하단 버튼이 여러 줄을 차지한다.** 390px 화면의 도구 모음은 108px, 하단은 113px이다. 320px에서는 도구 모음이 155px로 늘어난다. 일반 버튼을 단순히 줄바꿈해 놓은 방식이 문서 공간을 크게 줄인다.
4. **필기 기본 동작이 사용자 기대와 다르다.** 점을 찍어도 저장되지 않는다. 지우개로 선을 가로질러 드래그해도 지워지지 않는다. 둘 다 패키징된 앱에서 실제 재현했다.
5. **도구를 고른 뒤 속성을 빠르게 바꾸거나 현재 상태를 확인하기 어렵다.** 색상·굵기는 별도 메뉴 안에 있고, 도형을 선택해도 도구 모음에 현재 도형이 표시되지 않는다. 선택한 기존 필기의 색상·굵기를 바꾸는 흐름도 없다.

추천 방향: **Goodnotes의 읽기·필기 구분 + Drawboard의 도구/속성 분리 + PDF Expert의 모바일 도구 배치**를 LOXT의 SUIT·차콜·다크/라이트 토큰에 맞춰 적용한다. 참고 제품의 색상, 로고, 자산을 그대로 가져오는 제안은 아니다.

## 2. 확대 문제의 원인과 확인 범위

### 서로 다른 확대가 혼재한다

| 종류 | 현재 동작 | 확인 상태 |
| --- | --- | --- |
| PDF 하단 `+ / −` | PDF.js 문서 viewport와 필기 좌표 표시만 확대 | Windows 실제 재현: 정상 |
| PDF 맞춤 | 클릭한 순간의 영역 크기로 배율을 계산 | 실제 재현: 최초 계산 정상, 이후 리사이즈에 따라 재계산하지 않음 |
| iPad·휴대폰 두 손가락 확대 | PDF 배율을 바꾸는 로직이 없음. 선택 상태에서는 브라우저가 제스처를 처리할 수 있음 | 사용자 실기기 보고 + 코드상 확인. 이번 PC 자동 제스처에서는 전체 확대가 재현되지 않음 |
| 필기 도구 상태의 두 손가락 확대 | 필기 영역 `touch-action:none`, 별도 멀티터치 처리 없음 | 코드상 확인. Safari 실기기에서 조작별 추가 검증 필요 |
| PC Ctrl+휠·Ctrl+`+` | PDF 배율 변경 처리 없음 | 패키징 Electron의 자동 입력에서는 문서와 앱 배율 모두 변하지 않음 |

**확대 버튼 자체가 앱 전체의 배율을 변경한 것은 아니다.** 조사 실행본에서 PDF `+`를 누르면 문서 폭은 595→743.75px로 바뀌고, Electron 확대율은 1, 도구 모음 크기는 그대로였다. 사용자가 확인해 준 문제 조작은 모바일의 두 손가락 확대다.

브라우저는 기본적으로 핀치 확대를 처리하며, 앱이 직접 처리하려면 영역의 터치 정책과 포인터 이벤트를 함께 설계해야 한다. 이 설명은 공식 API 동작에 근거한 원인 추론이며, 이번 자동화로 Safari의 화면 배율을 직접 측정한 것은 아니다. [MDN touch-action](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/touch-action), [MDN 다중 포인터 확대](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events/Pinch_zoom_gestures).

### 권장 해결 방식

PDF 영역 안에서는 두 손가락의 거리 변화로 **문서 배율**을 변경하고, 두 손가락 중심 이동으로 **문서 위치**를 옮긴다. 로고·도구 모음·페이지 버튼은 같은 크기로 유지한다. 확대 중심은 두 손가락 중간의 문서 좌표로 잡아 확대할 때 보던 부분이 화면 밖으로 밀리지 않게 한다.

펜과 손가락 역할도 함께 정의해야 한다. 스타일러스 입력은 필기, 손가락은 이동을 기본으로 하고, 손가락으로 필기를 원하는 사용자는 명시적인 설정으로 선택하도록 제안한다. 손가락 필기 상태에서도 두 손가락이 들어오면 필기에서 확대·이동으로 전환하고, 제스처 시작 때문에 생긴 작은 점이나 선은 저장하지 않아야 한다. iPhone은 펜이 없을 수 있으므로 이 선택을 쉽게 제공해야 한다.

이벤트 제한은 PDF 캔버스 영역에 한정한다. 사이트 전체에 `user-scalable=no`나 `maximum-scale=1`을 넣어 해결하지 않는다. 앱 전체 글자를 확대할 필요가 있는 사용자를 위한 접근성 확대는 유지한다. 펜·텍스트 입력·브라우저 탭 안의 ChatGPT 등 다른 영역의 제스처를 가로채지 않는다.

추가 원인 후보: 모바일 페이지 번호·검색 입력은 12px 계열 글꼴을 상속한다. Safari는 키보드를 표시할 때 입력 영역을 확대·이동하는 동작도 있으므로, 핀치 문제와 별도로 입력 포커스 전후 `visualViewport` 검증이 필요하다. 이번 사용자 증상의 확정 원인으로 분류하지 않는다. 모바일 입력은 읽기 쉬운 16px부터 검토한다. [WebKit 입력 포커스 관련 설명](https://bugs.webkit.org/show_bug.cgi?id=195884).

## 6. 재현 가능한 핵심 버그

### P05 — 점이 사라진다

1. 예시 PDF를 열고 펜을 선택한다.
2. 문서의 한 지점을 누르고 움직이지 않은 채 놓는다.
3. 저장 완료 후 문서를 다시 확인한다.

기대: 작은 점이 남는다. 실제: 필기 객체 0개. 원인은 2개 이상의 points만 커밋하는 조건이다. 화면만 고치면 내보내기에서 점이 다시 빠질 수 있으므로 저장 데이터와 PDF 내보내기도 함께 점 처리해야 한다. 현재 PDF export는 선 구간 루프를 사용한다. [pdfs.cjs:74](C:/Users/simky/OneDrive/Dokumen/ChatGPT/buzz_interface/electron/pdfs.cjs:74).

### P06 — 지우개로 쓸어 지울 수 없다

1. 문서에 대각선을 그린다.
2. 지우개를 선택한다.
3. 선 밖에서 누른 뒤 선을 가로질러 움직이고 놓는다.

기대: 가로지른 선이 지워진다. 실제: 선이 남는다. 현재 지우개는 처음 누른 target이 `[data-object]`인지 검사하고 반환한다. 기본 개선은 스트로크 전체 삭제를 드래그로 지원하는 것이다. 부분 지우기는 별도 데이터/좌표 설계가 필요한 추가 기능이며 같은 규모로 취급하면 안 된다.

### P03 — 너비 맞춤 후 회전/리사이즈에서 다시 넘친다

1. 웹 화면 768px에서 PDF 맞춤 → 너비 맞춤을 누른다.
2. 같은 화면을 320px로 줄인다.

기대: 맞춤을 선택한 상태라면 새 문서 영역에 다시 맞는다. 실제: 문서 폭 697px, 배율 117%가 유지된다. `fitMode` 상태가 없고 한 번 계산한 숫자만 저장하기 때문이다. 사용자가 직접 확대했다면 리사이즈 때 배율을 함부로 초기화하지 않도록 두 상태를 구분해야 한다.

## 7. LOXT에 적용할 UI 제안

### 문서 헤더

앱 상단 로고·Work/Live·오른쪽 패널은 유지한다. 그 아래 PDF 헤더는 `보관함으로 돌아가기 / 제목 / 내보내기 / 더보기`를 한 줄로 구성하고, 긴 제목은 편집 전에는 말줄임한다. 이름 수정은 기존 기능을 유지하되 편집할 때만 충분한 너비를 제공한다. 상시 큰 제목 입력칸이 문서 공간을 차지하지 않도록 제안한다.

내보내기는 기존 원본/필기 포함 PDF 두 항목을 유지하고 주변 버튼과 같은 높이로 맞춘다. 상단 버튼이 본문을 덮거나 제목 아래로 단독 이동하지 않도록 레이아웃을 정한다.

### 도구 모음

기본 구성: 이동, 선택, 펜, 형광펜, 지우개, 텍스트, 도형. 각 도구는 기존 아이콘 스타일의 선 아이콘을 사용하고, PC는 툴팁에 이름·기존 단축키를 표시한다. 아이콘만으로 동작을 추측하게 하지 않고 활성 도구를 명확하게 표시한다.

펜을 고르면 색상 3~5개와 굵기 3개를 빠르게 선택한다. 상세 값은 그 도구의 속성 버튼에서 조절한다. 텍스트를 고르면 펜 굵기 대신 글자 크기, 도형을 고르면 현재 도형과 선 속성, 지우개는 지우기 종류가 나타난다. 현재 기능에 없는 속성은 비어 있는 장식 버튼으로 만들지 않는다.

기존 `Ctrl+Shift+P/E/H`, `T`, 실행취소/다시실행은 유지한다. 새 이동 단축키는 Space를 누르는 동안만 임시 손 도구로 전환하는 방향을 제안한다. 입력칸 편집 중에는 도구 단축키를 가로채지 않는다. 브라우저 탭 단축키와도 범위를 분리한다.

### 문서 영역·페이지

처음 열면 해당 컨테이너 너비에 맞춘다. PDF의 비율은 유지하고, 페이지 미리보기의 열림 여부·오른쪽 패널의 폭을 계산에 포함한다. 화면 회전·패널 폭 변경 시 맞춤 상태일 때만 재계산한다.

페이지는 기존 합의대로 열기/닫기만 가능한 패널을 유지한다. 데스크톱/넓은 태블릿은 옆 rail, 좁은 화면은 문서 위 overlay로 연다. 사용자 요청 범위를 넘어 페이지 편집·병합·삭제 기능을 추가할 이유는 없다. 현재의 한 페이지 보기 구조도 당장 유지 가능하다. 연속 스크롤은 긴 문서를 읽는 수요가 확인된 뒤 가상화를 포함해 검토한다.

반응형 기준은 기기 이름이나 창 전체 폭보다 **PDF에 실제 남은 폭**을 우선한다. PC의 오른쪽 패널에 좁게 열어도 동일한 compact 레이아웃을 적용해야 한다. 모바일 문서 내부에 LOXT 전체 탐색 풋바를 추가로 상시 노출하는 제안은 아니다. 현재 PDF 화면에서 풋바를 숨기는 동작은 문서 공간을 확보하므로 유지할 수 있다.

### 제안 와이어프레임 — PC / 넓은 태블릿

아래는 배치 제안이며 구현 화면이 아니다. 기호는 최종 아이콘을 뜻한다.

```text
┌ LOXT · Work                         기존 상단 패널 열기 ┐
│ ←  알고리즘 3장.pdf                     내보내기 ▾  ⋯   │
├ 페이지│이동 선택│펜 형광펜 지우개│T 도형 ▾│↶ ↷──────────┤
│       │           ● ● ●   얇게 보통 굵게  속성 ▾       │
├───────┬────────────────────────────────────────────────┤
│ 1 ▣   │                                                │
│ 2 ▣   │           PDF 문서 / 필기                       │
│ 3 ▣   │           문서만 확대·이동                      │
│       │                                                │
├───────┴────────────────────────────────────────────────┤
│ 검색       ‹  3 / 24  ›       저장됨       − 125% ▾ +   │
└────────────────────────────────────────────────────────┘
```

속성은 충분한 폭에서 한 줄 안에 합칠 수 있다. 항상 두 줄로 고정할 필요는 없다. 읽기 상태에서는 필기 속성을 숨겨 문서 공간을 늘린다.

### 글꼴·테마·크기

- SUIT와 현재 테마 토큰을 유지한다. 문서 원본의 글꼴·색상은 앱 테마와 별개로 보존한다.
- 제안 시작값: 문서 헤더 16~18px, 도구 이름/툴팁 12~13px, 상태 11~12px. 모바일 **입력칸**은 16px부터 검토한다. 실제 화면에서 조정할 설계값이며 최종 확정 수치가 아니다.
- PC 도구 hit area는 약 36~40px, 터치는 최소 44px를 기본 검토한다. 글자를 작게 해도 누르는 영역까지 줄이지 않는다.
- 둥근 정도는 현재 LOXT의 6~9px 계열과 얇은 테두리를 따른다. 모든 도구를 별도 큰 카드로 만들지 않는다.
- 도구 활성 상태는 작은 배경/테두리와 아이콘 상태로 구분한다. 일반 선택 드롭다운은 기존 합의대로 체크 + hover로 유지한다. 두 종류의 상태를 혼동하지 않는다.
- 다크 모드 용지 톤은 선택 사항이다. 기본은 원본 그대로, 내보낸 PDF는 보기용 톤 변경의 영향을 받지 않아야 한다. 전체 PDF에 단순 반전을 걸면 그림·사진·색상 의미가 바뀔 수 있다.

## 8. 기본 개선과 별도 확장 구분

**기존 PDF 기능을 정상적으로 다듬는 범위**

- PDF만 확대·이동, 최초/반응형 맞춤, 도구/하단 배치, 긴 제목/내보내기 크기.
- 점 저장, 드래그 지우기, 활성 도형 표시, 현재 색상/굵기 표시.
- 입력 종류 구분, 도구별 속성, 선택 객체 편집의 기본 흐름.
- 문서 상태 복원, 저장 상태, 접근성 이름/포커스.

**별도 기능 확장이므로 범위를 선택할 항목**

- 올가미/다중 객체 선택, 부분 지우개, 필압 기반 선, 손글씨 보정.
- 문장에 달라붙는 텍스트 형광펜·밑줄, PDF 링크/목차.
- Goodnotes/Notability 같은 별도 확대 필기 창, 도구 모음 사용자화.
- 연속 페이지 스크롤, 집중 읽기 모드, 보기 전용 용지 톤.

OCR·손글씨 인식·AI·페이지 병합/삭제·자동 도형 인식·네이티브 Pencil Pro 제스처 전체는 이번 UI 조사만으로 구현을 권장하지 않는다. Safari 웹의 펜 입력과 네이티브 앱의 기능을 동일하게 약속할 수 없다.

## 9. 구현한다면 권장 순서

1. **입력과 배율을 먼저 안정화**: P01–P03, P05–P07, P13. PDF 좌표 저장 형식은 유지하며, 페이지·필기·텍스트의 같은 변환 기준을 확보한다.
2. **도구/속성/반응형 배치 정리**: P04, P08–P12, P16–P20. 기존 테마를 유지하고 마우스/터치 표면을 함께 검증한다.
3. **보기 상태·검색·저장 경험 개선**: P14–P15, P23–P24. 외부 기기 동기화 보고서와 중복되는 원인을 함께 처리한다.
4. **측정 후 확장**: 많은 필기·큰 PDF의 입력 지연과 렌더링을 측정해 P22/P25/P26 범위를 정하고, 선택 기능은 별도 결정한다.

리스크: PDF zoom과 필기 좌표의 변환을 따로 고치면 저장·선택·내보내기의 위치가 달라질 수 있다. 제스처는 pen/touch/mouse 구분, 두 번째 손가락 진입, OS 취소, 페이지 변경 중 입력까지 함께 다뤄야 한다. UI를 먼저 재배치하고 입력 문제를 남기는 순서는 권하지 않는다.

## 10. 반드시 필요한 후속 검증

- 실기기 iPhone Safari·iPad Safari/PWA에서 두 손가락 확대 시 앱 UI 크기 유지, 확대 중심 유지, 양방향 이동.
- 펜 필기 중 손바닥/손가락 접촉, 펜을 놓고 이동, 손가락 필기 중 두 손가락 진입, 화면 밖으로 나갔다 복귀.
- PDF 25~400%에서 점/선/형광펜/도형/텍스트의 표시·선택·크기 조정·저장·PDF 내보내기 좌표 일치.
- 다크/라이트, 페이지 패널 열기/닫기, 오른쪽 패널 폭 변경, 회전, 긴 제목, 가상 키보드, Safari 주소창 높이 변화.
- 검색 결과 강조, 여러 일치 문장, 빈 결과, 이미지 기반 PDF에는 검색 가능한 텍스트가 없다는 안내.
- 굵기/색상 입력을 키보드와 보조기술로 조작, 포커스 복귀, 버튼 접근성 이름.
- 많은 필기에서 실제 입력→화면 지연, 장시간 필기의 점/메모리 증가, 많은 페이지의 초기 로딩/텍스트 추출.
- 기존 원본 PDF와 필기 저장 데이터 보존, 외부 변경 충돌 처리. 변경 후에도 기존 문서의 위치가 달라지지 않아야 함.

이번에 확인하지 않은 범위: 물리 iPad/iPhone의 Safari 제스처 계측, Apple Pencil 필압/손바닥 구분, VoiceOver/NVDA, 실제 대용량 PDF의 FPS/메모리, 타사 유료 제품 직접 사용, PDF 내보내기 결과 전체 비교. 웹 모의 화면의 핀치에서는 배율 변화가 없었으며, 이를 Safari 문제 해결 증거로 사용하지 않는다.

## 11. 유지해도 되는 구조

- PDF 원본과 별도 필기 객체 저장, 리비전 검사와 오류 복구 방식의 기본 방향.
- PDF.js canvas + 텍스트 레이어, 필기 객체의 PDF 좌표 저장 방식.
- 페이지 미리보기의 가시 영역 렌더링과 닫힌 패널의 작업 취소.
- Work/Live 같은 뷰어 사용, 사용자 보관함과 PDF 내보내기 원본/필기 포함 분리.
- SUIT·기존 다크/라이트 토큰·브랜드. 전체 편집기를 다른 제품으로 교체할 근거는 이번 조사에서 찾지 못했다.

일부 구현은 개선이 필요하지만, 이 구조를 유지하면서 입력/배율/도구 UI를 정리하는 접근이 가능하다.
