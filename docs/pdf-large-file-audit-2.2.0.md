# LOXT 2.2.0 큰 PDF·iPad 확대 멈춤 조사

조사일: 2026-10-09. 사용자 보고: 약 90MB PDF, PC 앱은 정상이고 iPad 웹 화면만 멈춤. 실제 사용자 PDF·기기 메모리·Safari 진단 로그는 받지 않았으므로 특정 메모리 초과/브라우저 종료를 확정하지 않는다. 앱·설정·사이트·버전을 수정하지 않았다.

## 결론

우선 의심되는 원인은 iPad에서 수행하는 **배율 변경마다 전체 페이지 다시 그리기 + 제한 없는 캔버스 픽셀 수 + 전체 문서 선행 검색 색인**이다. PC가 정상이라는 사실과 일치하는 클라이언트 병목이다. 서버 문제가 없다는 것을 모든 요청에 대해 증명한 것은 아니지만, 이미 열린 예시 페이지 확대에서는 원본 PDF 추가 요청 없이도 반복 렌더링 지연이 발생했다.

90MB는 압축된 파일 크기다. 페이지 이미지 해상도·투명 효과·벡터 수·문자 수·확대율·브라우저 캐시가 실행 메모리와 작업 시간을 결정한다. 90MB 자체가 동일한 실행 메모리나 렌더링 시간을 의미하지 않는다.

## 캔버스 메모리 계산

A4 예시 595×842 PDF 단위, 출력 비율 2, RGBA 4바이트/픽셀. 단일 픽셀 표면만 계산한 값이며 이미지 디코딩·PDF 바이트·worker·텍스트·GPU·이전 버퍼를 포함하지 않는다.

| 배율 | 캔버스 픽셀 | 단일 표면 바이트 |
| --- | --- | --- |
| 100% | 1,190×1,684 | 약 8.0MB |
| 200% | 2,380×3,368 | 약 32.1MB |
| 300% | 3,570×5,052 | 약 72.1MB |
| 400% | 4,760×6,736 | 약 128.3MB |

설치된 PDF.js 6.4.299의 완성형 viewer는 iOS/Android에 `maxCanvasPixels=5,242,880` 기본 제한을 적용한다. LOXT는 완성형 viewer 대신 core render를 직접 사용하므로 그 viewer 제한을 자동으로 상속하지 않는다. 단순히 getDocument에 같은 이름의 옵션을 추가해 해결되는 것이 아니라 LOXT 출력 배율/캔버스 크기를 직접 제어해야 한다.

## 실제 예시 측정

최종 Windows 2.2.0 패키지 + 승인된 별도 Edge 웹 프로필. 820×1180 CSS px, DPR 2, 8페이지 벡터/텍스트 예시 PDF 305,132바이트. 페이지당 사각형 4,000개와 텍스트 400개. 실제 사용자의 90MB PDF가 아니다. CPU 4배 제한은 인위적 시험 조건이고 iPad CPU와 동등하지 않다.

| 조건 | 확대 입력 | 캔버스 크기 재설정 | 완료된 렌더 표식 | 50ms 이상 main-thread 작업 | 손을 뗀 후 완료 관측 |
| --- | --- | --- | --- | --- | --- |
| Windows 기본 | 20회 이동, 2380ms | 20회 | 20회 | 18개, 합 1017ms, 최대 71ms | 136ms |
| CPU 속도 4배 제한 | 20회 이동, 5279ms | 20회 | 1회 | 40개, 합 4215ms, 최대 174ms | 464ms |

완료 표식은 canvas.dataset.rendered=true이며, rendering 효과의 마지막까지 도달했음을 뜻한다. CPU 제한 조건에서 재설정 20회 중 최종 1회만 완료 표식이 나타났다. 개별 PDF RenderTask의 내부 취소 횟수를 직접 계측한 숫자는 아니다.

두 조건 모두 확대 중 PDF 원본 추가 요청 **0회**. 이미 연 페이지에서도 UI 작업만으로 부담이 발생했다. 텍스트 DOM childList 변경 기록은 기본 16,000개, 제한 조건 800개였으며 정확한 텍스트 span 생성 개수와 동일한 지표는 아니다. 최종 표면은 2597×3675픽셀, 약 38.2MB였다. 브라우저 배율은 1 유지.

이번에는 실제 iPad 전체 멈춤·Safari 프로세스 종료·90MB 파일의 peak 메모리를 재현하지 않았다. 확정한 것은 비효율적인 반복 렌더 구조와 제한 없는 출력 크기, 예시 문서에서의 긴 UI 작업이다. 사용자의 현상과 맞는 가장 강한 원인 후보는 이 구조와 큰 PDF의 해석/이미지 메모리 비용이 함께 발생하는 것이다.

원시 결과: `test-results/pdf-zoom-audit-2.2.0/results.json`. 조사 스크립트도 같은 폴더에만 작성했고 앱 코드는 바꾸지 않았다.

## 권장 수정 순서

1. **가장 먼저: 제스처 표시/렌더 배율 분리.** 기존 PDF/텍스트/필기 레이어를 함께 CSS 변환하며 1프레임에 1번만 표시. 손을 뗀 뒤 약 150–200ms 안정화한 최종 배율로 한 번 렌더한다. 숫자는 제안이며 기기 시험으로 조정한다. 새 렌더 완료 전 기존 화면을 유지한다.
2. **동시에: 출력 픽셀 예산.** 모바일 초기 예산으로 약 5MP를 검토하고 출력 비율을 적응시킨다. 표시 배율은 유지하되 높은 배율에서 선명도가 제한될 수 있으므로 보이는 영역만 고해상도 타일로 그리는 방향을 검토한다.
3. **큰 문서: 전체 검색 색인을 iPad 오픈 경로에서 분리.** 현재 페이지 표시를 먼저 하고, PC의 별도 작업자에서 색인을 만들어 재사용한다. 아직 없으면 검색 요청 시 제한적으로 준비하며 표시/확대가 우선한다. 네트워크 요청·처리 작업에 실제 취소 정책을 둔다.
4. **캐시·수명 제한.** 유휴 페이지 리소스 정리, 제한된 텍스트/그림 캐시, 미리보기 가상화, 텍스트·링크 내용을 배율 변경마다 재구성하지 않도록 한다. 필요한 PDF 리소스를 render 중 cleanup하지 않는다.
5. **90MB 스캔 문서 대응.** 위 변경으로도 부족하면 PC가 표시용 페이지/타일 이미지를 생성하고 iPad는 가벼운 표시와 필기 좌표만 처리하는 경로를 검토한다. 원본 PDF/내보내기를 보존하며 PC CPU·캐시 용량 비용과 Work/Live 동시 사용을 검증한다.

‘페이지를 그리는 중…’ 문구만 숨기거나 확대율만 낮추는 것으로 원인이 해결되지는 않는다. 기존 페이지 좌표·필기·텍스트 선택·검색 강조·링크·확대 중심을 함께 맞춰야 한다. 다음 구현 검증에서는 사용자의 동일 문서로 처음 열기/재열기/200–400% 연속 핀치/페이지 이동/앱 화면 전환을 비교하고 Safari 원격 Web Inspector의 main thread·메모리/프로세스 상태를 확인해야 한다.
